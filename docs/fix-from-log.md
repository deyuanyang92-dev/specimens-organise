# 按错误日志修复（维护流程）

适用：用户发来 `crash_*.log`（闪退）、`gui_stall_*.log`（未响应）、`boot_fault.log`（原生崩溃）、
`startup_failure_*.log`（打不开），或直接粘贴报错文字。日志位置：帮助 → 打开崩溃日志目录
（`%APPDATA%\标本入库管理\`）。

**最高原则：修一个功能，不能破坏另一个功能。** 下面每一步都为这条原则服务。

## 1. 分诊（先判断要不要修）

```bash
python scripts/triage_log.py <日志文件>      # 或：python scripts/triage_log.py - 然后粘贴
```

- 看 `Version` / `Time`：**旧版本的日志**先看报告里列出的后续提交，多半已修复 → 请用户升级，而不是重复修。
  （2026-10-04 教训：启动提示曾把 v0.10.37 的旧日志当成新闪退弹出，差点重复修复。）
- 卡死类先要 `gui_stall_*.log`，"被占用"类先要弹窗原文。
- 证据不足时明说"未确证"，向用户要更多日志，不凭猜测改代码。

## 2. 复现（红）

写一个**失败的测试**，走日志里同一条调用链、注入同样的异常或条件（文件被占用、网络盘慢、
字段为空……）。确认它在当前代码上失败。不能复现就不要声称修好了。

## 3. 修根因（绿）

- 在**正确的层**修：例如"文件被占用"在读写层重试，而不是只在最外层 `try` 吞掉；
  界面层的兜底是第二道防线，不是替代品。
- **最小改动**：修复提交里不顺手重构、不改无关代码、不改界面外观。
- 旧逻辑按项目规范用 `# 旧：…` 注释保留，写明为什么改。

## 4. 同类排查

同一个缺陷模式往往不止一处（v0.10.40 只补了 3 处读取，审计又找到 5 处漏网）。
grep 同样的调用 / 同样的异常来源，一并修并各补测试。

## 5. 不破坏其他功能（回归防线）

1. **影响面**：列出被改函数的所有调用方（`grep -n "函数名(" specimen_app`），逐个确认行为不变；
   涉及数据格式的改动必须保证旧工作区仍能打开（项目硬约束）。
2. **不许为了变绿去改旧测试**。旧测试失败 = 改动破坏了已有行为。只有用户明确要求改变该行为时，
   才能修改那条测试，并在提交说明里写清是哪个需求。
3. **全量回归**：`python scripts/run_tests.py --isolate`（每个测试文件独立进程 + 单用例看门狗）。
4. **两个平台**：推到分支，等 CI（Windows + Linux）全绿才合并。很多问题只在 Windows 出现
   （文件占用、路径、弹框）——本地 Linux 绿不算数。
5. **发布门禁**：打 `v*` 标签后，发布流程会再跑一遍全量测试，不过不打包；打包后还会真实启动 exe。

## 6. 发布与回滚

- 每个修复独立分支、独立提交，提交说明写：日志文件名 / 版本 / 根因 / 新增测试名。
- 发布后若用户报告新的回归：**先 `git revert` 该修复并发布**，恢复到已知良好状态，再重新修。
- 修完告诉用户：根因（带证据）、修了什么、怎么验证的、哪些仍"未确证"、升级到哪个版本。
